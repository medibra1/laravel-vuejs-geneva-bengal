# Internationalization — three distinct layers

A recurring source of bugs in this project came from conflating these
layers, or from the routing layer's own caching interacting badly with
Inertia navigation. **Never let content editable by the client end up in a
vue-i18n `.json` file, and never let interface chrome end up in a
translatable database column.**

## Layer 1 — Routing (`niels-numbers/laravel-localizer`)

Public routes are registered inside `Route::localize(function () {...})`
in `routes/web.php` — this generates **two static routes per definition**
(a `with_locale.*` and a `without_locale.*` name pair), unlike the
originally-used `mcamara/laravel-localization` package, which resolved the
`/fr`/`/en` prefix dynamically per-request. The static-route approach is
what makes `route:cache` safe — see the migration note in `CLAUDE.md` for
why the package was swapped.

`SetLocale` → `RedirectLocale` middleware run **before**
`HandleInertiaRequests` in `bootstrap/app.php` — the `alternateUrls`
shared prop (hreflang, see [seo.md](seo.md)) depends on the locale already
being resolved.

**Admin routes are not locale-prefixed.** `routes/admin.php` has no
`Route::localize()` wrapper — a single internal client, always French, no
public/SEO reason to localize back-office URLs. See
[Layer 3](#layer-3--interface-chrome-vue-i18n) for what that means for
admin UI text.

### The FR→EN language-switch bug (fixed, but worth understanding)

`window.Ziggy` (the route table `route()` reads) is injected **once**, by
the `@routes` Blade directive, at the very first full page load. Since
route prefixes are locale-dependent, the server-generated Ziggy payload
differs per locale — but an Inertia `<Link>` navigation (the language
switcher used to be one) never re-triggers a full load, so `window.Ziggy`
stayed frozen on whichever locale loaded first. Every `route()` call after
switching languages kept resolving to the *old* locale's URLs.

**Fix**: the FR/EN switcher in `PublicLayout.vue` is a plain `<a>` tag, not
an Inertia `<Link>` — a genuine full browser reload, which regenerates
`window.Ziggy` correctly. This isn't a workaround to revisit; it's the
correct fix given that `window.Ziggy` is locale-dependent by construction.
Don't convert it back to `<Link>`.

## Layer 2 — Translated business content (`spatie/laravel-translatable`)

JSON columns on models: `Cat.description`, `Page.title/body/meta_title/
meta_description`, `FaqItem.question/answer`, `Testimonial.quote`. Edited
in the admin via FR/EN tabs (`LocaleTabs.vue`). This is real client
content — editable without a code deploy, stored in the database, subject
to the same sanitization/validation as any other admin-writable field
(e.g. `Page.body` goes through `mews/purifier`, see
[admin.md](admin.md#rich-text-editor)).

Deliberately **not** translatable: `Litter.notes` (free-text admin
scratchpad, not visitor-facing copy), enum-backed values like `Cat.type`
(internal, not displayed text).

## Layer 3 — Interface chrome (`vue-i18n`)

`resources/js/locales/{fr,en}.json`, compiled at build time, zero
server round-trip for a button label. **Public pages only** — the admin
deliberately has no `useI18n()`/`$t()` usage anywhere under
`resources/js/Pages/Admin/**`. This was a conscious scope decision
(confirmed twice with the client, most recently 2026-08-16: "on fait le
minimum" when asked whether to extend i18n to the back-office) — one
French-speaking client, no admin language switcher, ~20 admin page
components that would need it for zero real benefit.

Admin flash messages/validation strings are French, hardcoded directly in
PHP controllers (`->with('success', 'Chat créé avec succès.')`), not run
through Laravel's own `__()` translation helper — there's no
`lang/fr.php`/`lang/en.php` file structure for admin strings, since
nothing in the admin ever needs the English version. The two **public**
controllers that flash a message (`Public\ContactController`,
`Public\NewsletterController`) do use `__()`, backed by
`lang/fr.json`/`lang/en.json` (Laravel's JSON translation format, keyed by
the English source string).

### Locale must be set explicitly for anything sent from a queue/webhook context

`App::getLocale()` reflects the *current request's* locale — meaningless
inside a queued job or a Stripe webhook handler, which run in a totally
different context with no visitor attached. Any notification that must
respect a visitor's chosen language captures that locale **once, at the
moment a request from that visitor is actually being handled**, then
carries it explicitly:

- `Public\ContactController`/`NewsletterController`: `(new
  XxxNotification(...))->locale(app()->getLocale())` — called while still
  inside the visitor's own request.
- `Deposit.locale`: a real database column, set once in
  `Public\DepositController::confirmIntent()`'s metadata (see
  [payments.md](payments.md)) — because the mail that eventually goes out
  (`DepositConfirmedNotification`) is triggered later, by a Stripe webhook
  or by `ReconcileCheckouts`, neither of which has any visitor-locale
  context of its own by the time they run.

Staff-facing notifications (`DepositPaidNotification`,
`StripeReconciliationIssueNotification`, and the staff copy of
`DepositUnavailableNotification`) never call `->locale()` — staff is
always addressed in French.

## Reference — mail translation files

`lang/fr/emails.php` / `lang/en/emails.php` — structured PHP arrays (not
flat JSON) for multi-line mail bodies, used by
`ContactRequestConfirmedNotification`,
`NewsletterSubscriptionConfirmedNotification`, and
`DepositConfirmedNotification`/`DepositUnavailableNotification`'s
client-facing copy.
